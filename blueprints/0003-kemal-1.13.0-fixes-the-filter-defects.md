# 0003 — Kemal 1.13.0 fixes the filter defects; the design does not change

## Status

Accepted, 2026-08-24.

## Context

`docs/04-kemal-integration.md` is built on a constraint it calls "load-bearing, not a
footnote": four defects that each cause an authentication filter to silently not run, fixed
on Kemal `master` but absent from 1.12.0, plus a fifth — leaked multipart temp files when a
`before` filter halts.

**Kemal 1.13.0 was released on 2026-08-24 and contains all five fixes.** `shards install`
resolves it today under the existing `>= 1.10.0, < 2.0` constraint. From its changelog:

- `GET` filters now run for `HEAD` requests served by the `GET` route
  (GHSA-jf9q-62h3-924j). Filters run for both the request method and the method of the
  route that serves it.
- `Kemal::Handler` `only` / `exclude` are scoped by the serving route as well as the
  request method, so `only ["/admin/*"]` no longer lets `HEAD` past.
- `Kemal::Router` filters whose path ends in `/*` are registered: a trailing `/*` now marks
  a subtree.
- Router filters are registered once per path instead of once per route on that path, so a
  filter on a path carrying both `GET` and `POST` no longer runs twice.
- Multipart temp-file cleanup moved to `Kemal::InitHandler`, so it runs however the request
  ends — including a `before` filter that halts.

1.13.0 also adds the HTTP QUERY method (RFC 10008): a `query` route DSL,
`Kemal::Router#query`, and `before_query` / `after_query` filters. QUERY is safe and
idempotent but carries a request body.

## Decision

**The design does not change.** `docs/04-kemal-integration.md` already anticipated this:
"the constraint may relax, but the 'guard does its own method-agnostic matching' design is
safe either way and costs nothing." Three reasons it stands:

1. **The floor is 1.10.0, not 1.13.0.** `docs/00-scope.md` sets the Kemal floor at 1.10.0
   because `Kemal::Router` and path-specific `use` arrived there. Every application on
   1.10.0 through 1.12.0 still has all four defects. A library whose security depends on the
   consumer having upgraded is a library with a silent failure mode.
2. **Method-agnostic prefix matching costs nothing.** `AuthenticationHandler` registered
   globally and `PathGuard` matching `env.request.path` for every method is not a workaround
   that 1.13.0 makes redundant; it is simply the correct shape, and it is immune to the
   next defect in this area as well as the last one.
3. **New methods keep arriving.** QUERY did not exist when the guard rules were written. A
   guard that dispatches on an allowlist of methods would have silently not covered it. One
   that ignores the method entirely already does.

Two things do change:

- **Guard specs add QUERY** to the `GET` / `HEAD` / `POST` / `DELETE` set. It is a method
  that reaches routes and carries a body, and it is exactly the kind of addition a
  method-allowlisting guard would miss. `HEAD` remains in the set as the regression for the
  defects above, and must not be dropped now that upstream has fixed them.
- **`AuthenticationHandler` must not be registered at position 0.** Kemal 1.13.0 notes that
  a handler placed ahead of `Kemal::InitHandler` with `use handler, 0` owns temp-file
  cleanup for uploads it parses itself, because that position opts out of everything
  `InitHandler` does. The authentication handler has no business owning that.

## Consequences

- `docs/00-scope.md`'s CI main line moves to Kemal 1.13.0; the floor stays 1.10.0.
- `docs/04-kemal-integration.md` keeps its four-defect section, reframed: the defects are
  the reason for the design and they are still live for consumers on the supported floor,
  rather than a description of the newest release.
- The README warning stays, narrowed to "Kemal 1.10.0 – 1.12.0", with the advice to upgrade.
- The nightly CI job against Kemal `master` remains useful, and its original purpose —
  noticing when these fixes ship — is served.
- QUERY is safe and idempotent per RFC 10008, so it is **not** in the CSRF-protected set
  (`POST`, `PUT`, `PATCH`, `DELETE`). It carries a body, which makes it easy to mistake for
  a mutation; a spec asserts it is not treated as one.
